# 把微信群接龙名单落成「解析表 + 分单计划」（全链路）

## 任务

你会拿到某晚羽毛球的微信群接龙原文（`environment/jielong.txt`）、群友别名表（`environment/peers.json`）、已订好订单的快照（`environment/orders.json`）。请把接龙名单完整解析成「逐人解析表」，再按订单容量与下述规则生成分单计划，输出两个 JSON 文件。全程只做本地文件读写，不访问网络、不调用任何订场接口——只考察两个产物文件的内容。

本题是纯文件级任务：用文本编辑器、表格软件或脚本完成均可；CLI agent 与桌面端同样适用。

## 输入（三件，均为最终依据）

- `jielong.txt`：接龙原文（含标题行、名单行、追加段）。
- `peers.json`：`self_id`（发起人本人学号）与 `peers[]`（每条 `id` 学号 / `name` 昵称 / `aliases` 别名数组）。
- `orders.json`：当晚 4 张订单（2 场地 × 2 时段），每张含 `orderNo / venueSiteName / startTime / blockType / initiatorId / peers`（`peers` 为该单现有同伴学号）；顶层 `capacity_per_order` 为每张包场单的同伴上限。

## 产物

在运行目录写出两个 JSON 文件（UTF-8、无 BOM；放运行目录根目录或 `output/` 子目录均可）：

### resolution.json —— 逐人解析表

JSON 数组，按 `seq` 升序；每个名单行一个对象，字段如下（不多不少）：

| 字段 | 类型 | 说明 |
|---|---|---|
| seq | 整数 | 该行的原始序号（接龙行首数字） |
| raw | 字符串 | 该行去掉行首「序号 + 分隔符」后的原文（保留 emoji、全角字符、限定语原样） |
| sid | 字符串或 null | 映射到的学号（peers.json 的 id） |
| status | 字符串 | `"matched"` / `"unmatched"` / `"conflict"` |
| slots | 字符串数组 | 取值只有 `"19:00"`、`"20:20"`，升序、不重复 |
| note | 字符串 | 备注（要求见规则 9） |

### plan.json —— 分单计划

JSON 数组，按 orders.json 中订单的出现顺序，每单一个对象，字段如下（不多不少）：

| 字段 | 类型 | 说明 |
|---|---|---|
| orderNo | 字符串 | 订单号 |
| add | 字符串数组 | 将新增的学号，按接龙 seq 顺序 |
| skip | 字符串数组 | 已在单内、需跳过的学号 |
| reject | 字符串数组 | 无法加入的学号 |
| reason | 字符串 | 该单动作说明（规则 10 的要求） |

## 规则（按以下规则执行）

1. **行识别**：只把「数字序号 + `.` `、` `)` `）」开头的行当名单行；`#接龙`、形如 `M.D`（月.日）开头的日期行、`——` 开头的分隔行、「参与接龙」、空行一律不算名单。
2. **场次**：第一场 = 19:00，第二场 = 20:20。没写限定的人两场都加；写明「第 N 场」（含 `only` / `只` 前缀、全角数字）只加该场。
3. **到达时刻**：行尾形如 `H:MM` 的是到达备注，不是场次；按晚上语境理解，H < 12 时 +12 小时（如 `9:00` → `21:00`）。归一后的到达时刻落入哪个场次时段（19:00–20:10 / 20:20–21:30），就只加哪个场次。
4. **泛称**：昵称中含「朋友」的视为代他人报名的泛称 → `status="unmatched"`、`sid=null`，不许赋学号。
5. **昵称匹配**：昵称（去掉到达时刻与限定语后的部分）与 `name`/`aliases` 比对：原文相同，或「去首尾 emoji + 全角转半角」后相同，即命中；表情/emoji 原样登记的别名按原文命中。
6. **命中结果**：唯一命中 → `status="matched"`、`sid`=该学号；命中多个不同学号 → `status="conflict"`、`sid=null`；零命中 → `status="unmatched"`、`sid=null`。
7. **本人**：`self_id` 是发起人本人。接龙中的本人行 `status="matched"`、`sid`=本人学号、`slots=[]`、note 注明本人跳过，不进入任何分单名单。
8. **待人工**：`unmatched` 与 `conflict` 行保留在 resolution.json 中（slots 照常按规则 2–3 解析），但不进入 plan.json。
9. **note**：`unmatched` 行与本人行 note 非空；`conflict` 行 note 非空且必须列出全部候选学号；带到达时刻的行 note 必须包含归一后的时刻（如 `21:00`）；其余 matched 行 note 可为空串。
10. **分单**：每个场次按 orders.json 中的顺序先填靠前的单、溢出到靠后的单；每张包场单（`blockType=2`）须满足「现有同伴数 + 新增数 ≤ capacity_per_order」（发起人不占同伴名额）。目标人选已在某单现有同伴中 → 记入该单 `skip`（同场次幂等，且该单不再重复加此人）。溢出后无处可加的人：因散场单（`blockType≠2`）不可加同伴被拒 → 记入该散场单 `reject`；因包场单全部满员 → 记入该场次最后一张单 `reject`。`reject` 非空的单，`reason` 必须说明原因。
11. **日期**：接龙标题里的日期仅作参考，不作为筛单或分单依据；产物以 orders.json 的实际订单为准，无需输出日期。

## 交付

- 在约定运行目录写出 `resolution.json` 与 `plan.json`；
- 建议随附三件输入的原样副本与 `meta.json`（产品 / 版本 / 操作人 / 日期）；
- 回传时说明：产物位置、解析处置概览（matched / unmatched / conflict 各几人）、分单合计（add / skip / reject 各几人次），以及 unmatched 与 reject 人员的去向说明。
