**解释**：八场 0 分的直接原因是交付形式不符——题面要求以文件卡片交付，产品多数运行只以代码围栏或在会话内贴文交付；交付行为间歇性（bird r2c、dabstep r1c、bird r3 确实交付了卡片，分获 86.67 / 20.0 / 86.67），间歇性与 2026-11-01 的前端改版时间相关，但不能排除其他产品侧原因；最大调用轮次上限独立地截断了多个长任务。

**未排除因素**：前端改版可能同时改变了 agent 的产物交付管线与风控策略（改版前同产品曾以文件链接交付 bird 产物）；发送吞没门的触发机制未定性（与附件大小无关：6.4KB 附件被吞而 2.64MB 通过）；tb 内容门的具体触发词为产品黑盒；本机浏览器自动更新与网络抖动造成的环境插曲已逐槽记 verdict，但无法证明其对产品侧零影响。

**可复现实验**：同冻结题面 + 同输入包（SHA 随槽记录）重跑即可检验交付行为是否复现；tb 内容门可用「中性文本 + 同附件」对照「原题面 + 同附件」的发射成败重复判别（探针收据已随目录交付）；bird r2c 的 86.67 可由其交付的 answers.jsonl（15 行，13 对）经冻结 checker 复算；bird r3 的 86.67 同法可由其交付的 answers.jsonl（api-fileLink 收割）复算。
