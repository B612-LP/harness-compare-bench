# 桌面发射预检纪律（2026-10-31，r1103 预检三败后立制）

> 适用：所有桌面端（豆包办公/元宝专家模式/WorkBuddy）正式批与补测批的**发射预检**阶段。
> 立制缘由：r1103-formal-b3 预检三连败暴露发射层故障此前**无签名分类与处置判据**——r1101 发射失败（按钮点击 5 败）、r1103 发送成功但会话空目录（延迟创建）、冷启复现，三种签名在两个半月内先后出现，每个新批都要现场重新摸一遍。本文档把签名分类、处置矩阵与恢复判据前置成文，预检失败不再即兴决策。

> **根因更正（2026-10-31 11:34，L14 环）**：r1103 三败真实根因为**豆包产品时段额度耗尽**——probe 会话回复体明示「当前时段额度已用完，预计今日 04:38 恢复」（用户 11:26 截图实证）。S2「发送成功但会话空目录」是配额门的下游表现，立制时「agent 运行时未启动 / 产品 agent 服务层」的层次判读**不成立**，S3 冷启复现亦不构成服务层证据（额度门与进程态无关）。下表原文保留作立制时判断留痕，判读以本更正为准；诊断第一原则见第三节。

## 一、故障签名谱系（实证）

| 签名 | 实证批次 | 表现 | 层次判读 |
|---|---|---|---|
| S1 按钮点击失败 | r1101 doubao×exercism（10-30 23:35） | 「新工作任务」控件点 5 次仍未到达全新任务页 | 发射 UI 层（控件无响应/页面态异常） |
| S2 发送超时+空会话目录 | r1103 预检 #1/#2（10-31 02:48/02:51） | 发送动作完成，会话目录**延迟**创建（>30s 窗口）且目录**完全为空**——agent 运行时未启动 | 产品 agent 服务层（任务受理但运行时未拉起）**→ 根因更正：产品配额门（时段额度耗尽），非运行时故障** |
| S3 冷启复现 | r1103 预检 #3（02:54，pkill 完全退场后冷启） | S2 在干净进程态下复现 | 排除应用残留态 → 服务层结论加强 **→ 更正：额度门在冷启下同样复现（与进程态无关），不构成服务层证据** |
| S4 确认卡阻塞（会话有动作、产物不落） | r1104 预检（10-31 11:30，app v2.34.11 起） | agent 在跑（UI「已处理 N 分」），但工作区零产物、trajectory 0 字节；消息流挂「允许一次」终端确认卡 | 产品权限门：v2.34 新增 composer 权限模式选择器（始终询问=新版默认，编辑外部文件/联网逐次确认 / 按需确认 / 全部允许）。处置=批前把权限模式切到「全部允许」（与 v2.33 时代 b1/b2 实际行为面对齐），driver 已固化 ensure_permission_mode + 在途确认卡兜底点击；模式与 app 版本记入运行记录 |

对照成功基线：r1101（23:35–00:19 五场）、r1102 probe+正式场（01:18/01:27）同期签名全绿——失败与**时段/产品侧状态**相关（深夜时段假设仅记录不结论，样本不足）。

## 二、处置矩阵（预检阶段，零模型冒烟）

| 情形 | 处置 |
|---|---|
| probe 一次通过 | 正常进入注册→封印→运行流程 |
| probe 失败（任意签名） | **先读 probe 会话的产品回复文案**（见第三节第一原则）；允许**至多 1 次**间隔重试（可含完全退场冷启，间隔 ≥20s）；重试须换签名记录 |
| probe 失败且回复体含**额度/限流文案** | 产品配额门（S2-Q）：不是发射链路故障——按产品明示恢复时刻安排重试，不计入「连续 2 次失败」停批计数；恢复时刻已过后 probe 双绿即走 |
| 连续 2 次失败（非额度文案） | **停批**：不注册、不落合同、无 D 封印需求（「先注册后运行」且无运行）；按预注册 fail-closed 申报 |

> 立制说明：r1103 预检的三次有界尝试（含 1 次冷启重试）发生在本矩阵立制**之前**，属创制事件本身；本矩阵自落盘起为前瞻规范（此后预检按「失败 + 至多 1 次重试」即停批执行）。
| 停批后恢复判据 | **probe 连续双绿**（间隔 ≥10 分钟）方可在**新环**重新走注册→封印→运行；不得在同环内原地热复用旧封印。**更正（L14）：额度门（S2-Q）恢复以产品明示时刻为准，恢复时刻已过后双绿即满足，不做额外机械等待** |
| 运行中发射失败（已过预检） | 按批次 SAFE_POLICY（`infrastructure_invalid` 作废，配额制不重试） |

## 三、签名记录要求

**诊断第一原则（2026-10-31 用户纠正成文）：发射失败必先读产品回复体/会话内文案（额度、限流、登录、网络提示）再归因**——回复体是最直接的产品侧状态信号，不读回复体就归因「运行时/服务层」曾导致 r1103 误判（把额度耗尽当成发射故障）。

每次 probe 尝试记录：时刻、签名（S1/S2/S3/S2-Q/S4/其他）、**产品回复文案摘录**、会话目录创建与内容状态、应用进程态（pgrep）、退出码；收据存私档预检 JSON（`identity_value` 齐备，category=interface_preflight，零模型调用）。签名分类表随实证增量维护（本文件为 v1，根因更正记 v1.1，S4 权限门记 v1.2）。

**版本与配置披露（v1.2 增补）**：豆包 app 2026-10-31 两连跳自动更新（01:28 → 10:55 落定 v2.34.11），b1/b2 跑在 v2.33.7。v2.34 起新增：①composer 权限模式选择器（默认「始终询问」）；②任务运行时绑定 saman 沙箱环境；③trajectory 改为任务结束一次性落盘（运行中 0 字节，结束判定逻辑兼容、采集时序不变）。正式批以 probe 记录 app 版本与权限模式，产品版本变化在运行记录与报告中如实披露。

## 四、与其他纪律的关系

- 与[工作区边界判定线](<判定线-2026-10-31-桌面工作区边界.md>)独立：预检管「能不能发射」，判定线管「发射后行为边界」；两维各自判定。
- 与 SAFE_POLICY 的关系：预检失败发生在注册前，**不产生** `infrastructure_invalid` 事件（无注册即无导入）；SAFE_POLICY 只约束已注册发射。
- 预检 probe 为零模型冒烟（1 次微型往返属 `interface_preflight` 分账）；本文件不改变任何既有裁定与分数。
