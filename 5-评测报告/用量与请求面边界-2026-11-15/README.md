## 同尺寸两个会话：数字不能跨场套用

私档读取范围包括旧预注册及其事后修订、结果表、WB 执行器源码、两场各自的创建/提交回执、判卷、session-read、本地原始轨迹和对应调用保存的工具结果；仅离线读取，不执行旧脚本。依据各场回执、会话字段与工具调用/结果标识以及前后消息链，在私档核对了两场身份不相同；此处不公布标识或原日志。下表的使用量是记录在相应步骤的 `providerData.rawUsage.prompt_tokens`，是两个步骤的**差**，不是净增文件 token、字节或费用：

| 场次 | 可见动作与原始读数 | 差值 | 限制 |
|---|---|---:|---|
| 路径错误事故场 | 首次 Read 失败；第二次 Read 所在步骤 28,848，后续答复步骤 70,836 | 41,988 | 第二次 Read 之前的差值起点不是事故场首次 Read；首次步骤为 28,791；按旧分类器取事故场首末则为 42,045，不是 41,988。不能转给有效重跑场。 |
| 修正路径后的有效重跑（wb2，64k） | 一次 Read 所在步骤 28,794，后续答复步骤 70,733 | **41,939** | 原旧判卷的 usage 序列即为这两个数；旧结果表和公开数据却把事故场 41,988 放在此槽。 |

原始轨迹与 session-read 逐项一致，且轨迹文件摘要与 session-read 中记录的摘要相符；两个回执分别对应各自会话。这里的相符是本次私档内核对，不等于公开者能独立验真。事故重跑是修复提示路径造成的污染，不把两场合并成两个有效重复样本；各自回答均被旧判卷记为三键正确，这不足以证明整篇内容如何进入模型。

## 各层分别能说什么

1. **文件与本地工具结果**：夹具清单记载 65,504 B；本次读取文件并核对长度和清单摘要一致。两个会话各自同调用标识指向的本地工具结果文件均为 70,915 B；逐行去除行号后与夹具文本一致（比较时忽略末尾换行）。额外字节含行号等呈现，不能当请求字节。它们是**本地结果文件**，不是序列化的客户端请求体。
2. **本地轨迹观察面**：有效重跑的调用结果保存为持久化预览，旧判卷计其 JSON 序列化结果为 2,354 个字符（不是文件或请求体的字节数）；旧判卷显示头键在该结果、中键和尾键不在。随后答复的三个键与夹具一致。这个轨迹/回执是选定本地记录，不是完整发送体。
3. **旧分类器是启发式，不是正文验证**：源码依序收集有 `rawUsage.prompt_tokens` 的项，取最后一项减第一项；`full_tok_est = int(file_bytes / 2.5)`，实际门限 `int(full_tok_est * 0.9)`，达到即设 `model_side_full_inferred`。对 65,504 B 得 **23,580**；41,939 和 41,988 都超过它。注释写 0.95，代码实际为 0.9。该经验比例、门槛及记录间差值均不能反推出哪些字节进入请求；cache、其他上下文和消息构造等也未被该差值分解。
4. **请求面与服务端**：在上述 ring8 档案和该场本地会话目录的现存材料中，未发现能绑定同一会话、同一工具调用与后续消息的完整序列化客户端请求体；这不是对所有可能存储位置的穷尽证明。提交回执中的任务文本、使用量、预览、完整本地结果文件和三键答案都不能替代该请求体。**客户端是否发送全文 unknown；服务端接收、摄入与利用亦分别 unknown。**既不推定真实截断，也不推定真实全文，不将其他产品的机制迁移到此场。

要提高可识别性，需找到可信且完整的同槽后续客户端请求正文，能绑定调用和消息，并将其内容与源逐字节映射；若要证明服务端接收或利用，还需另有相应服务端证据。仅补更大的 usage 数、预览或答案并不足够。
