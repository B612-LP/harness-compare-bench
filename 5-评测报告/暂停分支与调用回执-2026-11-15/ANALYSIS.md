# 暂停分支与调用回执：13 条既有记录的离线派生分析

**性质：派生材料，不是原始轨迹，不是新增产品测试，不重算正式分数。** 本目录仅分析 WorkBuddy 的 13 条选定归档；不外推总体发生率、权限因果或跨产品性能。

## 1. 问题与观测面

问题是：`waiting_user` 在这些记录里更贴近 Read 信息拒绝，还是 Bash 调用未见结果？C02 的路线是否与 C01 相同？

[最小调用行表](<../../5-评测报告/暂停分支与调用回执-2026-11-15/derived.json>)包含 13 个匿名 attempt、64 个事件行及归档源文件 SHA-256。匿名 callkey 由私档固定的 conversation 与 callId 联合生成；不靠相邻位置、工具名或内容猜配。每个 attempt 的 conversation 映射只私存。公开行不含原始 ID、工具参数、输出全文、用户提示或私有路径。

13 份归档均自报 `sanitized_native_rows / selected_single_local_agent_trace`，offset=0、has_more=false、已载入数=该快照声明总数。**这只是所选本地快照的分页状态，绝非后台、全部 agent 或后续结果完整性证明。** A10/A11 没有独立最终状态文件，状态仅来自原判记录，表内标为 `judgment-only`。

**负控结论：** 4 条 waiting 全部出现 Bash 无结果；9 条 completed 均无 Bash 调用。Read 拒绝只有 1/4 waiting 出现，却在 8/9 completed 出现，因而在本表内不是 waiting 的必要条件；也不能据此说拒绝没有影响。

C01→C02 的两条对应关系 A02→A04、A03→A05 都发生了路线改变：Bash 不再出现，改为 Read 拒绝后定向 Grep，且都有配对结果与 completed 状态。私档补充核对为“归档记载的 fixture 哈希相同、只替换经过核对的 fixture 路径后提示相同”；**原提示字节不同**，不宣称严格等控重复。该提示/fixture 比较不能由此公开包独立复算。

## 3. 可以收窄什么、仍不能判定什么

- **可以收窄：** “所有等待都必须先发生 Read 拒绝”被这组反例推翻；“C02 只是原样重复 C01 路线”也不成立。与 waiting 最贴近的公开表内特征是 Bash 调用未见对应结果，而非一般工具无结果或 Read 拒绝。
- **H-action 仅是关联候选，不是批准机制确证。** 这里没有“Bash 有结果且成功”的对照；9 条负控实际均选择了非 Bash 路线。调用选择、任务状态与观察时点共同变化，不能估计执行 Bash 的因果效应。
- **状态来源层：** 11份归档状态文件只保留控制桥字符串，另2槽仅有旧判断标签；选档未保留完整原生 pending 响应与当时运行实现绑定。因此 waiting_user 不充当独立原生批准证据，同一标签在两份文件出现也不算两项独立来源。`comparison_ready=true` 仅表示派生结构与已知标签可进入表内比较，不表示原生状态来源已认证。
- **竞争解释保留：** 真实动作批准边界；采集在首次 waiting 即结束而产生的右删失；所选本地轨迹与状态更新不同步。后两者可以与批准机制同时成立。无回执自身不证明已触发权限弹窗、用户拒绝、命令执行失败或产品没有继续工作。
- **无法观察：** 真实等待/恢复时长与总成本均为 null，不填 0。轮询耗时不是任务真实等待时长；产品 usage 不充当输入摄入、成本或机制证据。显示文本字符数与 UTF-8 字节数分列，均不是模型输入量。
- **诊断不是终点：** 历史 `read_count` 曾按全部工具调用计数，尤其 C05 的 5/2 次工具调用实际上只有 3/1 次 Read。此命名差异不充当研究主要终点，也不回写旧分数或原件。

## 4. 表示去重与边界

30 个结果事件同时含 output 与 providerData 结果表示；其中 16 个显示文本表示不同。本包每个结果事件只计一次，选定 output 的 text/string（若缺 output 才后备 providerData），不将两者相加、不把两种表示当两次回执。显示字符/字节数只描述这个选定的解码表示，不描述模型看到的内容。公开 source hash 是归档文件的哈希，而不是从平台签发的真实性凭证。

## 5. 公开复算与私档缺口

[固定结果](<../../5-评测报告/暂停分支与调用回执-2026-11-15/result.json>)由[验证器](<../../5-评测报告/暂停分支与调用回执-2026-11-15/verify.py>)重算；[30 个逻辑/负例测试](<../../5-评测报告/暂停分支与调用回执-2026-11-15/test_verify.py>)覆盖重复/孤立/缺 key/身份冲突、局部缺页、单位混用、未知成本填零、结论篡改和自洽伪造边界。Python 3.9+，仅标准库；在本目录执行：

```sh
python3 -B verify.py
python3 -B test_verify.py
python3 -B -O verify.py
python3 -B -O test_verify.py
```

本次普通与 -O 模式均验证通过、各 30 测试通过。测试是派生表逻辑负例，不接触产品或模拟产品行为。

**公开可认证：** 这张已披露派生表是否按照所披露规则产生固定的投影指标，以及异常是否被保守处理。**30 个配对不是 30 次成功**；配对只表示 call/result 身份关系。固定结果没有锁定逐个结果的全部状态字段：例如将一个 result 的 `completed` 改为 `failed`，只要其他投影不变，当前固定结果仍可能完全相同。这是投影范围边界，不是逐行封印或来源认证；测试明确保留此反例。
