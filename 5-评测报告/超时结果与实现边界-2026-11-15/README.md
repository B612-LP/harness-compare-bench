# 超时结果与实现边界：豆包 LCB 三槽事后分析

**结论**：r2、r3 的私档执行回执均记 `abc389_g` 前 3/43 组通过、零基索引 3 首次超时；这相同的失败记录并不能证明两次由相同复杂度或同一原因造成。现存源码副本的静态结构既有相似也有差异，且其内容链并非运行时字节见证。分析是事后观察，不是预注册的因果检验；不新增产品/模型运行、不运行历史题解、不测时，也不修改历史分数。

## 观察、来源和分数口径

| 槽 | 公开 run 中产品场状态 | 公开 weighted / reward | 事后私档执行回执摘要（非公开可复算） |
|---|---|---|---|
| r1 | completed | 100 / 1 | 四题全过，`abc389_g` 43/43 |
| r2 | completed | 75 / 1 | `abc389_g` 3/43，首败 index 3，timeout |
| r3 | timeout | 75 / 1 | `abc389_g` 3/43，首败 index 3，timeout |

此处私档摘要来自已提供的非作者复核，不由本目录的公开脚本认证。历史公开 run 文件（复核脚本指明位置）本身含会话标识；此页不复制这些值，但引用旧源不能消除其既有公开暴露。公开 r1/r2 文件路径位于豆包批次，但其 `run_id` 内产品字段写作 `workbuddy`，r3 则写作 `doubao`；这是公开元数据不一致，不能仅凭该字段或目录闭合产品身份。独立复核在私档按槽核对了创建、等待与导出记录中的槽位关联、分槽导出目录及轨迹格式；这些可能同源的本地记录支持豆包来源，但不提供公开读者独立验真，也不是对历史运行时代码的证明，本分析不擅自修原件。r3 的**产品整场状态** `timeout` 和离线 checker 对**一组测试**的 10 秒 timeout 是不同的钟，不能互换。r2 的 after 清单是事后补记；原记录有关产品未中断只属自述，不由补记证明。r3 的 timeout 不能当作已完成会话。三槽是三个记录槽，不能据此声称三次统计独立。

[锁定 checker](<../../2-用例/lcb-recent-hard-4/checker.py>) 的 `run_problem` 对每题按测试列表 `enumerate` 零基顺序运行；每组子进程限时 10 秒；每组开始前检查该题累计耗时是否超过 240 秒，超出则记 `budget`。它不是严格的 240 秒整题硬截止：组内仍可用完整单组时限，末组结束后不会再作该项检查。遇到第一个失败即停止**该题后续测试**。`3/43` 是首败前通过了 3 组，不是测试了全部 43 组只通过 3 组。`timeout` 与 `budget` 是不同失败类型。单题全部测试通过才算通过；4 题各 25 分，至少 2 题且完整性守卫通过时 reward=1，因此 3/4 题对应 75 分且 reward=1，而不是该题取得 3/43 的部分分。

[truth](<../../2-用例/lcb-recent-hard-4/truth.json>) 的 `abc389_g.tests[3]` 是第 4 组，输入 `30 100000039`；`source: private` 是历史分类标签，并不表示这个已发布文件里的题库仍为私有。**仅在历史回执中索引语义确如上述 checker、当时实际采用对应锁定字节的条件下**，可以将 r2/r3 首败定位到这一组；现存公开文件的匹配并不证明历史进程实际加载了它们。

## 实现结构与不能决定的原因

非作者对私档现存副本所作的只读静态复核提供以下摘要，代码不公开复制：

| 槽 | 结构摘要 | 可以/不可以推出 |
|---|---|---|
| r1 | 90-bit 槽打包的大整数卷积 | 与另两份副本的卷积实现不同；100 分不证明其它实现的超时成因 |
| r2 / r3 | 均为 BFS 分层动态规划加逐系数朴素卷积；预处理及标签选择各异 | 存在有限结构相似，不是相同源码、相同复杂度或相同根因的证明 |

可竞争的解释包括实现中具体计算量或常数与限时相互作用、解释器/机器调度及负载差异、运行时实际输入或文件身份与记录不一致等；这些并非已确立的原因，彼此也不必互斥。公开观察没有逐段耗时、运行时加载字节的独立见证或可比较的环境记录，不能判定哪项主导，更不能排除其他因素；超时前 3 组输出正确也不能证明整题无正确性错误。不从输入规模臆测渐进复杂度或断言必然超限。

旧[失分谱](<../派生分析-豆包lcb失分谱-20261109/README.md>) 对 r2/r3 作过“同类算法复杂度”“两轮独立”等更强解读；本次以这里的较窄结论为准，不改旧稿。另有不同场次的[历史回放说明](<../../4-打分细则/判卷回归/replay-all-README.md#5-首跑两次执行的观察lcb-负载抖动实录>)称 r1029 同产品同题两遍回放分别为 75 和 100，第一遍记录 #3 timeout，并将差异归作负载抖动；该记录显示限时结果可能对回放条件敏感，不是对本三槽负载或超时机制的测量与证明。

## 内容链与私档缺口

已提供的非作者复核称：三槽各自现存题解副本与对应 after 清单记录的哈希相同，after 清单哈希与各私档 execution 的 `frozen_after_sha256` 相同；各公开 run 的 `execution_receipt_sha256` 与对应私档 execution 回执哈希相同。这是**自报内容链**：支持当前副本与当前回执之间的内容对应，不证明采集时间、未被遗漏的历史状态或进程当时加载的字节；尤其不能把 r2 事后清单说成当时实时封存。

三份私档 execution 记载引用同一 lock，其哈希为 `e2f52839c444f9e7430110ddae26e719e0c59a89d57fd432901801bff2bc36d7`。公开 [lock](<../../4-打分细则/可信冻结-20261031-wb-v2/freeze.lock.json>) 的实际哈希与该值一致，且其 checker、truth pin 与当前公开字节一致。公开 run 本身只给出私档回执哈希引用，不包含私档执行明细；因此公开读者不能从这个包独立复核私档哈希对应、源码结构、首败明细或实际运行环境。lock 是内容绑定，不是独立可信时间戳或执行证明。

## 公开只读复核

在仓库根目录运行（仅 Python 标准库）：

```sh
python3 -B '5-评测报告/超时结果与实现边界-2026-11-15/verify.py'
python3 -B -O '5-评测报告/超时结果与实现边界-2026-11-15/verify.py'
```

[verify.py](<verify.py>) 只读公开文件：核 lock 固定哈希及指定 checker、truth、题目输入三项 pin 和字节；用 AST 仅解析 checker 顶层字面量，不导入或运行 checker；核题序、各测试列表计数、历史标签计数及 checker 使用的规范序列化哈希、零基第 3 项输入；核对三份公开 run 的状态、分数、reward 和原样引用的私档执行回执哈希。未遍历 lock 其余 pin，也不把有冲突的 `run_id` 产品字段用于身份认证；脚本不访问私档、不复制会话标识、不运行历史源码。脚本通过只说明这些**公开内容核对通过**，不认证私档、不证明历史运行时身份或结果真实性；checker 的首败与计分行为需结合其锁定源码人工审阅。

本次在普通及 `-O` 模式各运行一次，均通过；另在内存中注入 lock 字节、测试列表、索引 3（重算列表哈希）、分数、回执引用五类漂移，两种模式均拒绝。代码自审确认检查不依赖 `assert`，不会因 `-O` 被移除；这些负例并非穷尽性安全证明。
