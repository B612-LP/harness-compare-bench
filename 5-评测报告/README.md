## 本仓报告的定位（重要）

CLI 赛道是**方法验证 / 学习**阶段：用两款有 CLI 的产品把「出题 → 闸门 → 判卷 → 取证 → 归因」整条链路跑通。因此本仓产出的是**阶段报告**，标题与正文须如实写明「阶段一：方法验证与 CLI 结果」，**不得写成五款竞品的最终横向评测**。

桌面赛道（WorkBuddy / 元宝 / 豆包）取证方式仍在设计，采集完成后另出阶段二报告，再合并为五款终稿。

## 写作前提（缺一不可）

1. `2-用例/` 用例已过 nop=0 / oracle=1 闸门（两例已满足，四道闸门全过）。
2. `3-表现现场/` 有对应现场且证据可复核（当前：Codex / DSH / 裸模型基线，两批模型）。
3. `4-打分细则/` 口径冻结后再打分（避免看着分数定标准；打分表 v0.3 已冻结）。
4. 归因链完整：模型（同模型对照 A 组）→ SKILL（环境层留档）→ Harness（A−C 差值）。
5. 每条结论的引用必须落在**仓内路径**；无法复核的历史材料进 `未知登记.json`，不进正文证据链。

## 口径边界（必须在正文声明，不许省）

- 结论覆盖范围：**CLI 赛道 / 两款产品 / 两用例 / 两批模型**，不外推为五款综合排名。
- 桌面端 GUI 手工执行与 CLI 自动批跑形态不同，横向比较须单独披露。
- 两款用例被两款产品**全部打满（满分饱和）**，说明本批用例区分度不足，只能支撑"能力达标"结论，不能支撑"谁更强"的排序结论。
- 成本口径：LiteLLM 无 GLM/MiMo 定价，`cost_usd` 为 null，按官方费率离线换算并注明取数日期。
- token 口径：统一为 `input + cached` 复算（Codex 的 input 含缓存、DSH 的 prompt 不含），**不得直接比较原始字段**；复算与更正过程见 v1.0 §5.2。
