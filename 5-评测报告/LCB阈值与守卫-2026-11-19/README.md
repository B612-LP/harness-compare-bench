# LCB：阈值诊断与输入守卫各自说明什么

**六条记录中的阈值诊断都有冲突，但这不是六次产品失败。** r1030 的两条及 r1031 的四条 LCB 都登记 4/4、阈值 2、二元奖励 1。旧矩阵的阈值子诊断却都预期 0。公开判卷输出另有 `input_integrity` 记录为真，说明明确写的是“附带输入副本与 canonical 一致”，不是从奖励倒推的。这只核验已记录的守卫，不证实历史运行时实际读取过哪份输入。

## 1. 同一码数不能跨单位使用

本次固定 4 题。如果计数阈值是 2，先看通过数是否至少为 2，再要求输入守卫通过。若只在这个固定分母下换写为比例，则应使用 0.5；将同一个数值 2 直接拿来与比例比较，五种通过数全部不满足。下表仅列出计数／比例门，未把守卫并入：

| 通过数 | 0 | 1 | 2 | 3 | 4 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 通过数 ≥ 2 | 否 | 否 | 是 | 是 | 是 |
| 通过比例 ≥ 0.5（仅这四题等价） | 否 | 否 | 是 | 是 | 是 |
| 通过比例 ≥ 2 | 否 | 否 | 否 | 否 | 否 |

钉住的公开 LCB 源码使用“通过数 ≥ 2 **且**输入守卫通过”；钉住的公开复核器以 `earned / possible` 与阈值直接比较。它们解释了冲突的形状，**不认证历史复核器的实际加载代码**：两张矩阵声明的历史工具 SHA 都不等于当前公开复核器的固定 SHA。六条加权分重算子检查均记通过；两批所选六槽的历史整体检查仍为 **2 通过／4 不通过**，这里未改状态或旧分。

## 2. 守卫能核哪一层

- 6/6 有零权重、类型为布尔的独立 `input_integrity` 报告项；附带副本匹配的报告与“未附副本，未核验，不扣分”是两种路径，不能只比较真值。本次六条都报告前者。收据嵌入同一份报告，不是第二个独立见证。
- 六个 stdout 路径指向**同一个 Git blob**。复核的是六条记录和各自的来源绑定，而不是六份差异化输出，更不是六次重新核验。收据声明的 checker SHA 与本次固定公开 checker 锚匹配，但不认证历史进程或当时文件字节。
- 若只改一条内存记录，把“仍有 4/4”配给明确失败的守卫，计数仍达标而模型化奖励为 0；删掉守卫项则无法得知奖励门是否成立。把同分的另一轮收据接在原槽，来源核对拒绝。非作者另核了守卫通过位的类型近错：保留 4/4 和登记奖励，只把布尔值换成单元素数组，不能采纳为真守卫。
