# Harness 竞品评测阶段报告（一）：用 CLI 赛道验证评测方法与归因链路

> **版本**：v1.0（2026-10-21）｜**上一版**：骨架 v0.1（2026-10-20，保留为历史）
> **覆盖范围**：Codex / DSH / 裸模型基线；**2/5 产品、CLI 形态、2 用例、2 批模型**
> **一句话**：本报告验证的是评测方法链路（出题 → 闸门 → 判卷 → 取证 → 归因），**不是**五款竞品的最终横向排名。

## 摘要

1. **做了什么**：用两款有 CLI 的产品（Codex 0.162.1、DSH 0.2.0-rc.2）＋两条自建用例，把「出题 → 闸门 → 判卷 → 取证 → 归因」整条链路跑通；判卷器在本轮被当作被测对象单独加固。
2. **得出什么**：两产品四份产品现场全部 reward=1；裸模型基线 0/2。A−C 增量 = 满分，说明**工具循环的执行权在 Harness**，而不是模型单独能完成的。
3. **过程面**：表观 token 量级差（Codex input 3.4–4.8 万 vs DSH prompt 0.2–0.8 万）主要来自**计价口径**；统一口径（input + cached）后为 1.18–2.09×，且 Codex 首轮注入 `<skills_instructions>`（SKILL 层），不能记到 Harness 头上（§5.2）。
4. **边界**：只覆盖 2/5 产品、CLI 形态、两用例满分饱和，**不构成五款排名**；桌面三款未采集。
5. **下一步**：桌面端最小闭环取证 + 一道行为探针题 + 五款终稿前置条件（§7）。

## 1. 评测问题与边界

### 1.1 公告要求 vs 本报告覆盖

公告要求比较五款产品（Codex、WorkBuddy、DSH、元宝专家模式、豆包办公）并说明差异、得分及理由。本报告只覆盖其中 2 款，且都是 CLI 形态，覆盖矩阵如下：

| 产品 | 是否采集 | 评测面 | 证据位置 |
|---|---|---|---|
| Codex | ✅ | CLI：两用例 × 两批模型（glm / mimo） | `3-表现现场/r1016-*-codex/`、`r1016x-*-codex/` |
| DSH | ✅ | CLI：两用例 × 两批模型（glm / mimo） | `3-表现现场/r1016-*-dsh/`、`r1016x-*-dsh/` |
| 裸模型基线（对照） | ✅ | GLM / MiMo 直连 API，零脚手架（C 组） | `3-表现现场/r1016x-*-bare/` |
| WorkBuddy | ⏸ | 桌面端：取证方式未定 | — |
| 元宝专家模式 | ⏸ | 桌面端：取证方式未定 | — |
| 豆包办公 | ⏸ | 桌面端：取证方式未定 | — |

### 1.2 为什么先做 CLI 赛道

三款桌面产品没有 CLI，GUI 取证（录屏、提示词留档、产物判卷）方案尚未验证。若先做桌面，一旦结论不成立，很难分清是「产品不行」还是「证据不足以支撑归因」。CLI 赛道能以最低成本把**判定链路**验证到可复核：同一用例、同一模型、同一评分器，A 组（有 Harness）与 C 组（裸 API）直接对照，差值就是脚手架的贡献。这一步的产出是**方法**，不是竞品结论。

取舍上，本阶段刻意不做五款横向比较：桌面取证规范未定，硬做只能得到不可复核的结论。把资源投在判定链路与证据链上，后续桌面与五款终稿可以直接复用同一套判卷器、运行记录与未知台账，减少重复建设。

### 1.3 归因定责的三层设计

- **模型层**：A 组两款产品接同一模型（glm-5.3-flash 批、mimo-v2.6-flash 批），同模型内两产品的差异只能落到 Harness。
- **SKILL 层**：环境冻结留档；本轮无自定义 skill，但 Codex 默认注入 `<skills_instructions>`，按 `4-打分细则/归因定责.md` 必须记在 SKILL 层（见 §5.2）。
- **Harness 层**：A − C，C 组为裸 API 直问（零系统提示、零工具、零循环），同一评分器判卷。

四值状态（`Harness 造成 | 模型造成 | SKILL 造成 | 无法归因`）逐条落表，见 §5.3。

## 2. 用例与判定标准

### 2.1 两条用例的观察点

| 用例 | 层次 | 观察点 | 陷阱 |
|---|---|---|---|
| `int-sum-sort` | 基础 | 文件读写 + 输出格式精确性（每行一个整数、恰好一个结尾换行） | 无 |
| `word-freq-report` | 中等 | 多步文本规则实现 + 自我验证 | 平票决胜（`a`/`dog`/`tests` 同为 5 次，恰好卡 Top-5 边界） |

两用例都规定「任务、输入、完成条件」三件事（公告原文要求）。一条基础、一条中等，是为了先验证「格式与确定性判卷」再验证「多步规则 + 自我验证」，难度阶梯小步推进，出错时更容易定位是判卷问题还是产品问题。v0.3 起正式判分入口是 `2-用例/<题>/checker.py`（产物目录判分），同目录 `spec.md` 记录观察项/权重/行为锚点，`truth.json` 记录 canonical 输入 SHA-256 与期望值；Harbor `tests/test.sh` 保留为历史实现。

### 2.2 三道闸门与二值口径

| 闸门 | 观察项 | 判定标准 | 不达标处置 |
|---|---|---|---|
| 1. 空跑准入（nop） | 空操作 agent 的 reward | 必须 = 0 | 用例作废（存在白给分路径） |
| 2. 参考解门（oracle） | 参考解 `solve.sh` 的 reward | 必须 = 1 | 用例作废（完成条件不可达） |
| 3. 正式评分 | 产品 × 统一裁定模型的 reward | 按用例细则判定 | 进入归因：模型 / Harness / 环境 |

headline 只认确定性 verifier，LLM judge 不进 headline；两用例均为 **binary 口径**（全 PASS=1，任一 FAIL=0，不给部分分）。四个闸门现场（两用例 × nop/oracle）全部通过，见 §4.1。二值口径的代价是丢失区分度信息；本轮保留 binary 是为了与 v0.2 已冻结的历史分对齐，同时 `checker.py` 仍输出 weighted 参考分供诊断。后续区分度题可启用 partial 模式，但同一题在评分期内不得切换口径，切换必须升版本并在 CHANGELOG 登记。

### 2.3 判卷器也被测试：v0.2 的 4 个漏判与 v0.3 修复

本轮把判卷器当被测对象做了一次审计。方法是先写「能变红」的负例：构造与正确产物只差一处规则违规的样例（折叠、空行、缺结尾换行、篡改输入、平票错序），先用旧判分器跑出通过结果复现缺口，再交给新版检查；同时保留一条正向参考解产物做 oracle 回归，防止「全部拒绝」式的假修复：

| # | 攻击样例（期望：拒绝） | 旧 v0.2 | 新 v0.3 | 修复项 |
|---|---|---|---:|---|
| 1 | 排序块折叠成一行（`8 17 23 42 56 99`） | **1（漏判）** | 0 | `format_strict`：每行一个规范整数 |
| 2 | 排序块中间插空行 | **1（漏判）** | 0 | 同上，空行不再被 `sed '/^$/d'` 洗掉 |
| 3 | 篡改 `input.txt` 后自洽作答 | **1（漏判）** | 0 | `input_integrity`：输入副本 SHA-256 守卫 |
| 4 | 缺结尾换行 | 0（碰巧） | 0 | v0.3 有显式结尾换行断言与准确报错 |
| 5 | 篡改 `corpus.txt` 后自洽作答 | **1（漏判）** | 0 | 输入完整性守卫（同上） |
| 6 | 平票决胜写错（`tests` 顶掉 `dog`） | 0 | 0 | 陷阱设计有效，已固化进 `--selftest` |
| 7 | 参考解产物（正向） | 1 | 1 | oracle 回归通过 |

新版判卷器 `--selftest`：int-sum 11/11 PASS、word-freq 11/11 PASS、轻量判卷模板 8/8 PASS。**结论**：旧版对 4 个攻击样例误判为通过（#1/#2/#3/#5），新版全部拒绝；正向与陷阱识别不受影响。历史现场仍按 v0.2 记录，v0.3 不做静默重判（避免「看着分数改标准」），只做自测、oracle 回归与只读复算。

### 2.4 环境层冤案的处置原则

任何 0 分先读 `verifier/test-stdout.txt`，确认「测试到底跑没跑」再谈模型行不行。历史教训：2026-10-13 的一次演示跑中 verifier 现场联网下载工具失败，测试未跑即判 0——这属于环境层失误，不是模型层失败。该次原始日志未入仓，作为方法教训登记在 `未知登记.json#env-v1-verifier-download`；本报告不把它当作任何产品结论的证据。

## 3. 变量控制（可复核性）

1. **同模型同协议**：Codex `wire_api="responses"`、DSH `openai-responses`，两批模型各自统一。
2. **联网关闭**：Codex `disable_web_search=true`；DSH 禁用 web 工具。
3. **权限形态对齐**：Codex `--dangerously-bypass-approvals-and-sandbox` ≡ DSH `danger-full-access`。
4. **版本锁定**：Codex 0.162.1 / DSH 0.2.0-rc.2，不符即拒跑。
5. **环境同构**：同镜像、同代理 overlay v2、超时 3×、同评分器。
6. **模型身份可查证**：DSH 无 `--model`，模型走配置 patch，每个 trial 的 `config.json` 留快照。

每条现场都带 `config.json`（配置快照）、`result.json`（成绩 + 时间线 + token 账）、`verifier/test-stdout.txt`（判卷现场）、`agent/trajectory.json`（行为链）四层证据，可按「标准阅读顺序」复核（`3-表现现场/README.md`）。这些控制的作用是把「产品差异」尽量压缩到 Harness 一个变量上：同模型去掉模型差异、同镜像与超时去掉环境差异、权限对齐去掉交互差异；剩下压不掉的（模型身份、缓存、skills 注入）写进未知登记，而不是含糊带过。

本轮新增三项可复核性：①判卷器 `--selftest` 负例（§2.3）；②运行目录输入副本 SHA-256 守卫（改输入直接 0）；③运行记录的行为分 JSON（schema v1，`validate_run.py` 校验），为桌面端行为分提供与 CLI 同尺的结构化记录。

## 4. 结果

### 4.1 闸门结果

四道闸门全过：int-sum nop=0 / oracle=1；word-freq nop=0 / oracle=1。证据：`3-表现现场/r1016-{intsum,wordfreq}-{nop,oracle}/<trial>/verifier/reward.txt`。

### 4.2 产品表现（两批模型）

**批次一（2026-10-16，glm-5.3-flash）**：

| 现场 | 用例 | Harness | reward | 步数 | input / output / cached |
|---|---|---|---:|---:|---|
| `r1016-intsum-codex` | int-sum-sort | Codex 0.162.1 | 1 | 8 | 43,003 / 706 / 27,328 |
| `r1016-wordfreq-codex` | word-freq-report | Codex 0.162.1 | 1 | 7 | 34,938 / 558 / 21,248 |
| `r1016-intsum-dsh` | int-sum-sort | DSH 0.2.0-rc.2 | 1 | 5 | 5,452 / 452 / 15,168 |
| `r1016-wordfreq-dsh` | word-freq-report | DSH 0.2.0-rc.2 | 1 | 6 | 7,758 / 2,318 / 21,824 |

**批次二（2026-10-16，mimo-v2.6-flash，含 C 组）**：

| 现场 | 组 | reward | 步数 | input / output / cached |
|---|---|---:|---:|---|
| `r1016x-intsum-bare` | C 裸模型 | 0 | 2 | 90 / 52 / 0 |
| `r1016x-wordfreq-bare` | C 裸模型 | 0 | 2 | 310 / 329 / 0 |
| `r1016x-intsum-codex` | A Codex | 1 | 7 | 36,022 / 1,000 / 32,448 |
| `r1016x-wordfreq-codex` | A Codex | 1 | 9 | 48,382 / 736 / 46,528 |
| `r1016x-intsum-dsh` | A DSH | 1 | 5 | 2,207 / 305 / 19,456 |
| `r1016x-wordfreq-dsh` | A DSH | 1 | 6 | 2,384 / 581 / 27,200 |

> 表内 token 为**各现场原始口径**：Codex 的 input 含缓存读，DSH 的 prompt 不含缓存（cached 单列）。统一口径与复算见 §4.4、§5.2。

**运行计数口径**（与周报、附录对齐）：本仓入库独立运行 **14 场 = 产品 A 组 8 + C 组 2 + 闸门 4**；结果层 **有效 14、失败 0、未知 0**。另有 2 次安装步网络故障的失败尝试**未入库、不计入运行数**，登记为未知项 `env-netflake`。评分条目（每场 6 项 PASS/FAIL）**不等于**运行次数，不重复计数。

### 4.3 C 组失败形态（A−C 的关键证据）

裸模型两次都产出了「要调用工具」的文本，但没有执行者：

- int-sum：开场白 + `cat /app/input.txt` 的工具调用块；
- word-freq：整段 Bash 工具调用块包着 Python 脚本（分词、标点集合都与规格一致）。

两次都是 API 层 `status: completed` 的合法回答，但都不是交付物。**工具循环的执行权在 Harness 手里**——这就是 A−C 增量满分的来源。另外，C 组两次回答都只用了 2 步（一次模型调用），说明失败不是「尝试后放弃」，而是从未获得执行机会。

### 4.4 过程面：步数与 token

- **步数**：Codex 8/7（glm）、7/9（mimo）；DSH 5/6（glm）、5/6（mimo）。同用例下两款产品接近，单批无法据此排序。
- **token**：原始表观差距大（§4.2），但这是计价口径造成的，见 §5.2 的复算。
- **耗时**：产品单场总耗时 3.4–7.1 分钟，其中环境准备约 2–3 秒、agent 安装 2.6–6.2 分钟、agent 实际执行仅 0.2–1.3 分钟——**时间方差几乎全部来自「每 trial 现装 agent」**，这是后续改用预装基础镜像的直接依据（§6）。需要提醒的是：agent 执行时长只反映模型实际干活的时间，不含人工操作；桌面端手工执行时，这部分会变成可观察的交互时长，不能与 CLI 的自动执行直接比。

## 5. 归因与讨论

### 5.1 A−C 增量 = 满分

A 组 4/4 满分、C 组 0/2。同一模型、同一评分器，唯一变量是「有没有 Harness 的工具循环与文件落地能力」。C 组能写出规则正确的脚本（word-freq 的标点集合都对），却没有任何机制执行它、写盘、再自查。**脚手架贡献的上界 = 满分**；本批用例上，模型裸能力为零，Harness 决定成败。这个结论不依赖对模型强弱的评价，只依赖「执行权有无」这一可观察事实：C 组知道要读文件、会写脚本，缺的只是读—执行—看结果—修正的闭环。

### 5.2 token 差异：现象 → 线索 → 验证 → 未排除变量

**现象（旧稿的说法）**：Codex input token 3.4–4.8 万，DSH 0.2–0.8 万，跨两批模型稳定复现 → 曾据此推断「Harness 层编排规模差异」。这个说法在 2026-10-21 被复算推翻，过程如下。

**线索 1（口径）**：两列数字的计价口径不同——`3-表现现场/README.md` 早已注明「Codex 的 cached 含于 input；DSH 的 cached 与 input 分列」。旧稿直接比较了「含缓存」与「不含缓存」两个量。

**线索 2（恒等式验证）**：用每个现场 `trajectory.json` 的 `final_metrics` 验证归一化方式：

- Codex：`total_tokens = prompt + completion`（43,003 + 706 = 43,709 ✓，cached 27,328 已含在 prompt 内）；
- DSH：`total_tokens = prompt + completion + cached`（5,452 + 452 + 15,168 = 21,072 ✓，cached 单列）。

因此统一口径为 **input + cached**；可复算脚本 `复算/token-recompute.py`（带 `--selftest`）。

**验证（重算四个切片）**：

| 模型 | 用例 | Codex 统一输入 | DSH 统一输入 | 含缓存比 | 未缓存比 |
|---|---|---:|---:|---:|---:|
| glm-5.3-flash | int-sum-sort | 43,003 | 20,620 | 2.09× | 2.88× |
| glm-5.3-flash | word-freq-report | 34,938 | 29,582 | 1.18× | 1.76× |
| mimo-v2.6-flash | int-sum-sort | 36,022 | 21,663 | 1.66× | 1.62× |
| mimo-v2.6-flash | word-freq-report | 48,382 | 29,584 | 1.64× | 0.78× |

**结论**：①「量级差 6–20 倍」不成立，统一口径后是 1.18–2.09 倍；②「跨模型稳定复现」也不成立——未缓存口径下 mimo/word-freq 的比值小于 1（DSH 反而更多）；③判断降级为「**计价口径差异 + 每轮固定开销差异**」，不能记为 Harness 编排规模差异。

**未排除变量**（因此归因标「无法归因」，见 §5.3）：缓存命中率差异；每轮固定前缀（system + 工具 schema + skills 指令）的大小与调用轮数；Codex 首轮 metrics 不完整；Codex 的 `<skills_instructions>` 属于 **SKILL 层**注入（见 `r1016x-wordfreq-codex/*/agent/trajectory.json` 第 1 步），不能记到 Harness。要坐实「Harness 编排规模」，需要只改一个变量的对照（固定缓存状态、或剥离 skills 前后重跑）；本轮没做，所以不下结论。

### 5.3 四值标注

| 观察项 | 四值 | 依据 |
|---|---|---|
| 产物完成度（A 4/4 vs C 0/2） | **Harness 造成** | 唯一变量是工具循环/执行权；C 组写了正确脚本也无法执行 |
| 工具选择与写后自查行为 | 无法归因 | 未做 SKILL/Harness 消融，只有单轮轨迹观察 |
| 步数差异 | 无法归因 | 单批一次运行，无重复测量，差异在噪声范围内 |
| token 用量差异 | 无法归因 | 计价口径 + 未排除变量（§5.2） |
| 安装步失败（2 次尝试） | **环境造成**（非模型/非 Harness） | 失败发生在 agent 安装阶段，重跑后成功 |

### 5.4 不能归因的项

单轮满分无法区分「模型强」与「Harness 提示词强」；SKILL 消融未做（本批无自定义 skill，Codex 默认 skills 注入未剥离）；B 组（各产品原生模型）未跑，模型层在本批只能靠 A/C 对照间接约束。以上全部登记在 `未知登记.json`。

## 6. 局限与置信度

1. **覆盖**：2/5 产品、CLI 形态、2 用例、2 批模型，样本小，不能外推五款排名。
2. **区分度**：两用例被两产品全部打满（满分饱和），只能证明「都会做」，不能支撑「谁更强」的排序。
3. **桌面缺口**：三款无 CLI 产品未采集，行为面证据（录屏/截图/对话记录）能否支撑归因尚未验证。
4. **闭源卡点**：WorkBuddy / 元宝 / 豆包不能换底层模型做对照，模型层无法钉死，只能靠同任务多轮 + 行为面证据降低不确定性。
5. **成本口径**：`cost_usd=null`（LiteLLM 无 GLM/MiMo 定价），只能按官方费率离线换算并注明取数日期。
6. **环境方差**：每 trial 现装 agent（2.6–6.2 分钟）占总耗时大头，agent 执行仅 0.2–1.3 分钟；安装步网络故障是本批唯一失败来源（未入库 2 次）。
7. **判卷器一般正确性**：v0.3 只对已知攻击面自测（每用例 11 组样例 = 1 正例 + 10 负例），未见攻击面仍未证；新题必须带负例才准入。
8. **归因强度**：token 差异只做到「排除口径假象」，未做单变量对照；「Harness 编排规模」仍是假设。
9. **置信度分级**：A−C 增量（高，直接对照）；判卷器修复（高，可复跑）；token 口径更正（高，恒等式可验）；桌面与五款结论（无数据，不评价）。
