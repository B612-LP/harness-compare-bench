## 1. 评测问题与边界

### 1.1 公告要求 vs 本报告覆盖
- 公告：五款（Codex、WorkBuddy、DSH、元宝专家模式、豆包办公）＋说明差异、得分及理由。
- 本报告覆盖：**2/5**，且为 CLI 形态。用表格如实列出覆盖矩阵（产品 × 是否采集 × 评测面 × 证据位置）。

【素材】`README.md` 覆盖状态表；`0-公告原文.md`。

### 1.2 为什么先做 CLI 赛道（方法验证动机）
- 三款产品无 CLI，桌面取证方式未定；若先做桌面，会在「证据够不够支撑归因」上卡死。
- CLI 赛道能以最低成本把**判定链路**（闸门、确定性判卷、轨迹取证）验证到可复核，再复制到桌面。
- 这一步的产出是**方法**，不是竞品结论。

【待填】用自己话写动机与取舍（可引周报第 1 期「本周难点突破」）。

### 1.3 归因定责的三层设计
- 模型层：A 组两产品接**同一模型**（glm-5.3-flash / mimo-v2.6-flash 两批），差异只能落到 Harness。
- SKILL 层：环境冻结留档（版本锁定、权限形态、联网开关、代理 overlay 一致）。
- Harness 层：**A − C**，C 组为裸 API 直问（零脚手架）。

【素材】`4-打分细则/归因定责.md`（三层定义 + 四值状态列）；`1-评测方案/2026-10-16批次-CLI赛道方案.md` 一、二节。

## 2. 用例与判定标准

### 2.1 两条用例的观察点
| 用例 | 层次 | 观察点 | 陷阱 |
|---|---|---|---|
| int-sum-sort | hello | 基础读写 + 末尾换行精确性 | 无 |
| word-freq-report | 中等 | 多步文本规则实现 + 自我验证 | 平票决胜（a/dog/tests 同 5 次卡 Top-5 边界） |

### 2.2 三道闸门（oracle-gating）
- 闸门 1：nop 必须 = 0（否则存在白给分路径）。
- 闸门 2：oracle 必须 = 1（否则完成条件不可达）。
- 闸门 3：产品分，仅认确定性 verifier；LLM judge 不进 headline。
- 二值口径：全 PASS=1，任一 FAIL=0，不给部分分。

【素材】`4-打分细则/打分表.md` 一、二节；`2-用例/README.md`。

### 2.3 环境层冤案的处置原则（写进方法贡献）
- 任何 0 分先读 `verifier/test-stdout.txt` 确认「测试到底跑没跑」。
- 教训案例：v1 冤案（verifier 现场联网下载失败 → 未跑即判 0，属环境层而非模型层）。
- 本批环境层实例：批次二安装步网络故障两份 codex 重跑，证据留痕。

【素材】`4-打分细则/打分表.md` 第一节原则 3；`3-表现现场/README.md`「环境层留痕」。

## 3. 变量控制（可复核性）

逐项列出并说明为何这样控（每项 1–2 句）：
1. 同模型同协议（Codex `wire_api="responses"` / DSH `openai-responses`）。
2. 联网关闭（Codex `disable_web_search=true` / DSH 禁用 web 工具）。
3. 权限形态对齐（Codex `--dangerously-bypass-approvals-and-sandbox` ≡ DSH `danger-full-access`）。

5. 环境同构（同镜像、同 overlay v2、超时 3×、同评分器）。
6. 模型身份可查证（DSH 无 `--model`，走配置 patch，快照留证）。

## 4. 结果

### 4.1 闸门结果（先证用例有效）
四道闸门全过：intsum nop=0 / oracle=1；wordfreq nop=0 / oracle=1。

### 4.2 产品表现（批次二，含 C 组）
| 现场 | 组 | reward | 步数 | input/out/cached |
|---|---|---|---|---|
| intsum-bare | C | 0 | 2 | 90 / 52 / — |
| wordfreq-bare | C | 0 | 2 | 310 / 329 / — |
| intsum-codex | A | 1 | 7 | 36,022 / 1,000 / 32,448 |
| wordfreq-codex | A | 1 | 9 | 48,382 / 736 / 46,528 |
| intsum-dsh | A | 1 | 5 | 2,207 / 305 / 19,456 |
| wordfreq-dsh | A | 1 | 6 | 2,384 / 581 / 27,200 |

### 4.3 三个可写的观察
1. **满分饱和**：A 组 4/4 全 1，两用例对两款产品均无区分度 → 只能证明「都会做」，不能排序。
2. **C 组的失败形态**：裸模型两次都输出"要调用工具"的文本块（`cat /app/input.txt`、包 Python 的 Bash 块），API 合法返回、但无执行者 → **工具循环执行权在 Harness**。
3. **token 量级差异（2026-10-21 更正）**：表观 Codex 3.4–4.8 万 vs DSH 0.2–0.8 万主要来自计价口径（Codex input 含缓存、DSH prompt 不含）；统一口径后 1.18–2.09×，且首轮含 `<skills_instructions>`（SKILL 层），**不能记为 Harness 编排规模差异**——判定降级为「计价口径 + 每轮固定开销差异」，未排除变量见 v1.0 §5.2。

【素材】`3-表现现场/README.md` 两批次汇总表 +「归因读法」；各现场 `agent/trajectory.json`。

## 5. 归因与讨论

- **A − C 增量 = 满分**：脚手架贡献的上界（本例中两用例都靠 Harness 才能落地）。
- **Harness 内差异**：两产品都满分，差异落在过程成本（token、步数）与行为模式（写后自查、工具选择）。
- **不能归因的项**：单轮满分无法区分"模型强"与"Harness 提示词强"；SKILL 消融未做（本批无自定义 skill）。
- **四值标注**：对每个观察项标 `Harness 造成 | 模型造成 | SKILL 造成 | 无法归因`，禁止含糊。

【素材】`4-打分细则/归因定责.md` 四值状态列。

## 6. 局限与置信度（评审最看这节，别缩水）

1. **覆盖**：2/5 产品、CLI 形态、2 用例、2 批模型，样本极小。
2. **区分度**：两用例满分饱和，无法支撑排序结论；下一步需加难度阶梯（大输出、多轮改需求、失败恢复）。
3. **桌面端缺口**：三款无 CLI，行为面证据（录屏/截图/对话记录）能否支撑归因未验证。
4. **闭源卡点**：WorkBuddy / 元宝 / 豆包不能换底层模型做对照 → 模型层无法钉死，只能靠"同任务多轮 + 行为面证据"降不确定性。
5. **成本口径**：`cost_usd=null`，离换算有误差，须注明费率取数日期。
6. **环境层残留**：每 trial 现装 agent（3–6 分钟）是时间方差来源。

【素材】方案四节「已知口径缺口」；`3-表现现场/README.md` 备注。
