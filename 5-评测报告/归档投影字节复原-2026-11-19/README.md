# 次包 JSON 投影能恢复多少原始字节？

**判断。** [同一历史六对研究](<../首包平衡与次包单叶置换-2026-11-19/README.md>)核过规范值闭合和原始长度差。本项另问：归档 JSON 投影在**不拿对应原件来挑序列化**时，能否预测该客户端捕获次包的精确字节？只重用既有档案，不新增运行，不是新机制干预。

**证据。** 固定第一对两臂作选择，另外五对的十份次包作留出。事前冻结九种候选；本次预测进程只取留出投影和已选编号，先封存逐目标 SHA-256 预测，随后另一进程才读对应原始捕获。十份留出的严格类型 JSON 值与收到的对象键顺序各一致 10/10。直接去除字符串外空白的规则是训练并列时的固定首选，复原原始字节 10/10；按收到的键顺序作紧凑 UTF-8 序列化且不加终止 LF 也精确命中 10/10，两者本批并列。仅改为递归排序时，10/10 长度相同但 0/10 逐字节匹配；用 ASCII 转义或加终止 LF 的候选也均为 0/10。

**反例。** 实际形状的内存副本只加入合法 JSON 空白：字节改变、严格类型值和顺序不变，同一解析后投影规则得到完全相同的字节。另一副本只改一个定宽字符串字符：原长和结构相同，严格值不同。独立合成对照另证实合法字符串转义也可丢失原始拼写，旧二进制浮点解析还可能合并不同的精确十进制值。这些对照未发射，也不是新增样本。

**限制。** 旧捕获器将同一请求缓冲区解析后另存保留键序的缩进 JSON；按旧公式重核，12/12 产生相同存档投影。过去的分析读过这些原件。本次仅让留出参考延后读取，不是独立语义构造或首次见到原件，不能支持普遍恢复、完整请求独立重建、来源认证、服务端实际输入、token、费用或 Harness 因果判断。路径白名单不是操作系统级物理隔离；封存后查固定 24 个叶项，不同 inode 24、两类交集为零、未观察到硬链接，但不能排除历史或瞬态别名。未改旧门、原件或评分。

**可复核范围。** [聚合件](<evidence.json>)只有计数、候选编号和布尔结论；[校验器](<verify.py>)仅复核固定计数与声明，不重建原件或认证链路。编号 1 是直接最小化；2–9 按「收到的键顺序／递归排序」×「UTF-8／ASCII 转义」×「无／有终止 LF」排列。项目内非作者从固定档案独立复核，不代替老师要求的受控第三方原档核验。
