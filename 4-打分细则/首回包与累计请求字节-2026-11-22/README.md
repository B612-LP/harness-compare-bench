# 首回包变小，不代表真值抵达时请求更小

对同一 16,000 B 输入文件的四次既有 DSH 运行，按首次绑定工具结果（E1）、首次工具结果直接给出同一校验值（E2）、可见主任务末请求（E3）对齐。两次内联的首结果已含校验值，E1＝E2；两次省略中段的首回包不含该值，之后各有一次查询原输入的工具调用。首工具结果按解码后的 UTF-8 字节计；累计量从初始主请求数到对应端点（包含该端点），只计**客户端捕获的 HTTP 请求正文字节**，不是服务端实际摄入、token、费用或缓存命中。

| 既有运行 | 首工具结果解码 B | 到 E1 累计原请求 B | 到 E2 累计原请求 B | 到 E3 累计原请求 B |
|---|---:|---:|---:|---:|
| 内联 1 | 16,000 | 126,423 | 126,423 | 126,423 |
| 内联 2 | 16,000 | 127,293 | 127,293 | 127,293 |
| 省略 1 | 1,931 | 96,203 | 135,326 | 135,326 |
| 省略 2 | 1,931 | 96,053 | 136,649 | 177,509 |

11 条主任务请求计入；另有 4 条各 34,133 B 的标题请求，单独记账。省略首回包只保留输入头、尾各 844 B，省略 14,312 B；1,931 B 包括回包附注。四种内联—省略对照复用同四次运行，不是四次独立试验。

## 为什么方向不同

- **原请求：**按预先固定的两对，省略组在 E1 分别少 30,220／31,240 B，之后多出 39,123／40,596 B 的主请求，到 E2 反而多 8,903／9,356 B。其余两种对照方向相同；四种 E2 差值为 +8,033 至 +10,226 B。这是同序号前缀与额外整包的分账，不是假定前缀内容相同。
- **删去会话事件字段的字节重算：**仅从原始 JSON 删除 `dsh_session_log` 及相邻分隔符，不重序列化、不发请求。到 E2 四种仍多 17,813 至 18,087 B，逆转不只由该字段占用造成。只计原 JSON `messages` 的 value 时，到 E2 则反而少 9,534 至 9,808 B。字段不同，不应合成一个「上下文成本」。
- **新结果与旧历史：**省略 2 到 E2 后再发一包，40,860 B；最新工具结果只有计数。该请求的历史仍含此前校验值，因此全文搜索会把它误计作一次新恢复。首次有效的两次补查都读原输入；虽然两份留存副本与输入字节一致，本例**不是**打开留存副本才恢复。

## 怎么复核、结论到哪

使用原档按同会话、调用标识、参数、对象、成功结果和请求顺序连接七条工具链；再对原请求正文定位 JSON 字段字节区间，将语法与非目标字段分开。非作者在本地从四份原档独立复算，区分了「正文带着旧值」与「最新结果交付新值」。公开页给出端点、字节和可手算等式；不公开原始请求、命令或挑战值。这不是外部第三方核验。层级定义见[统一观测规范](<../Harness统一观测规范-2026-11-19/README.md>)。

这组运行给出一个反例：不能用首回包或单个字段替代同一结果端点的累计主请求。这只是四次既有运行的事后分账，并非固定后续工具动作与内容的随机对照；不能据此认定省略设置造成了额外请求或字节增加，也不推论普遍方向。未新增运行、不改正式评分。
