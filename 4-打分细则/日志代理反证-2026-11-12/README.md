# 日志代理的条件反证与可区分边界（2026-11-12）

本项是[日志计量有效性](<../../5-评测报告/日志计量有效性-2026-11-12/README.md>)的离线逻辑附证，不是新增产品实验，也不是第三次独立的产品效果研究。新模型在分析前确定问题、发送切点、计量面与反证分支；历史日志问题则属事后发现。依据[原观测定义](<../请求侧观测规范-2026-11-08/README.md>)及[重复口径澄清](<../机制重复口径澄清-2026-11-12/README.md>)，不回写旧协议、分数或正式25格。

## 1. 回答的问题

S3/R3 相同，是否足以唯一决定最终请求字节？反过来，代理变化是否必然意味着请求变化？若新增与发送身份绑定的 body 观测，是否真能排除竞争解释，而不是恒定输出“不可识别”？这里检验这些推断的逻辑充分性，不识别真实产品采用了哪个发送策略。

## 2. 控制、模型与复核

- 两份定义源固定于 `52b5e81531f3171292240a01c4ef3e4cb4b84eb8` 的路径/SHA；新实现及结果是之后的派生件，不宣称已存在于该基线。来源绑定见[result.json](<result.json>)。
- 最强反例的 `L` 明确是**发送变换前的源事件账**，不是最终发送 item 副本。三策略使用完全相同的 `L`、canonical UTF-8 JSON、固定模型/工具声明/思考声明及切点 `K=[2,4,6]`；K 是已到达 source payload 数，**不由 usage 边界推导**。每次 renderer 仅收到切点前缀，不能访问未来内容。
- 候选为保留完整历史、删除已闭合旧调用/返回对、将返回正文替成外部引用。所有请求须通过本地受限的 Responses-like 结构与顺序状态机：初始 developer/user、注册工具/参数、唯一 call_id、先调后返、无悬挂调用；不是官方 API 合规认证，也不证明真实模型会产生同一输出。若 L 本来就是最终发送副本，此反例不适用。
- metadata 只按顶层白名单处理，不递归删除 arguments 内的业务 id/metadata 或 output；参数中的重复键、NaN 被拒。源对象前后深比较，交换策略运行次序仍相同；有未来内容非干扰正控。
- [verify.py](<verify.py>)仅标准库、只读两份源文件，不导入旧工具、不联网、不调用产品；默认 stdout，`--output NEW.json` 独占创建、拒绝覆盖。[test_verify.py](<test_verify.py>)普通与 `-O` 均38项通过；实际 CLI 与公开 result 逐字节一致。

```bash
python3 -I -S -B '4-打分细则/日志代理反证-2026-11-12/verify.py' --root .
python3 -I -S -B '4-打分细则/日志代理反证-2026-11-12/test_verify.py'
python3 -I -S -B -O '4-打分细则/日志代理反证-2026-11-12/test_verify.py'
```

## 3. 实际结果与可推翻分支

所有数字来自实际运行的新模型，不是产品请求测量。

| 构造 | 实际观察 | 能改变的判断 |
|---|---|---|
| 两个完整日志不同，但选中的 S3 相同 | S3 都442B；工具正文8/800B，声明的 toy sender body 662/1454B | S3 未计工具返回，不能由其相同推出实际输入相同；此行不声称完整 L 相同 |
| 同一完整源 L、同一 K、三 renderer | R3 都1003B；三次 body 合计 full=2542B、drop=2214B、reference=2075B | 在已声明源日志层与候选类中，L/R3 不能唯一决定请求字节；不证明真实产品兼容哪种策略 |
| 只改日志 seq/time | S3 442→470B，toy body SHA 相同 | 代理变动可能仅来自日志元数据 |
| 只加顶层 payload.id | R3 1003→1112B，三个 body 均相同 | R3 会计入发送器可剥离的日志字段；不允许借此抹除业务字段 |
| 相同有序文本拆成两叶 | R3 1003→1035B，声明的拼接 sender body 相同 | 包装敏感，不是同日志或真实模型语义等价证明 |
| 只移动 usage 标记 | R3 总1003B不变，分段 `[306,325,372]`→`[111,520,372]`；独立 K/body 不变 | usage 分段不是已证发送切点；这是算子试验，不证明两 trace 都符合真实 usage 语义 |
| 改可见任务正文 | S3 与 toy body 都变 | 正控，避免检测器对真实内容变化也恒定不变 |
| 增加与 request_id/K/源前缀绑定的 body bytes/SHA | 无收据3候选；仅q1仍3；仅q2剩2；q3剩1；不匹配收据剩0 | 新证据可缩小候选，不能恒喊不可识别；0只表示不符合这三种候选，非产品错误 |

三策略逐请求 bytes 为 full `[510,838,1194]`、drop `[510,838,866]`、reference `[510,692,873]`。这只是一组见证：无旧交换时 drop=full，短 output 引用化反而可能更大；等长度也不等 body 相同，均有实际负控。引用不等于回读成功。

## 4. 限制与证据等级

这是有限候选类下的构造性反证，不是概率估计、真实 HTTP 重建、产品召回/隔离测试、模型能力或费用比较。局部 schema、顺序配对和前缀因果性只是**结构兼容**，不等于同一真实模型输出可复现。相同拼接文本也不等于语义等价。

新增 body 指纹的正分支只在声明的三个 renderer 内区分；哈希不是全空间数学单射，不认证采集者/原件真实性，也不保证已捕获最终发送阶段或服务端实际上下文。对真实 r1109，仍需逐请求最终发送体、阶段/版本、尝试/重试身份与源项映射，不能以本模型替代这些缺口。实际 thinking/cache、token、成本仍未知。

## 5. 判断前后与下一步

此前“代理相同/变化”很容易被误读为真实输入相同/变化；现在八项实际模型分别给出反例、正控与新增观测的可区分分支。结论不是“真实请求永远不可识别”，而是“在当前证据层不能作该推断；何种额外绑定观测会改变它”已有可机验判据。作为 A/B 日志分解的逻辑附证使用，不增加产品 n、不据此追加重复批、不升级外溢因果结论。
