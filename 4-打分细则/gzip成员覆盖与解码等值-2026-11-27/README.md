# gzip：解码等值不证明消费了全部成员

[此前跨解析器校准](<../wire请求面扩展-2026-11-27/README.md>)的 6 份既有 gzip 客户端响应，Python 与 Node 整包解码一致。本次从同一批固定原件逐成员回算：**6 份原件都是单成员，均消费到归档正文末尾，且无未识别尾字节。** 因此原件上的 6/6 一致，无法区分完整读取与只解首成员的实现。

归档 gzip 正文合计 4,782 B，解码 56,287 B；六份响应共 178 个已派发数据帧（172 个 JSON、6 个 Chat `[DONE]`），六条流均通过[固定有限终态门](<../SSE终态与内容完备分账-2026-11-27/README.md>)。成员边界、CRC32、ISIZE 与原始/解码字节摘要分开登记。这里的原 SHA 只承诺归档 gzip 正文，不包含外层 HTTP 分帧、采集前传输或源站出处认证。

## 在同一正文上只改容器

| 固定派生 | 完整消费与正文 | 只解首成员会怎样 |
| --- | --- | --- |
| 改 MTIME（6） | 容器摘要变；同样的解码字节、数据帧与有限终态 | 不丢内容，因为仍是单成员 |
| 中点分为两个成员（6） | 容器摘要变；拼接后正文逐字节同 | 6/6 只给严格前缀；有限终态皆不通过 |
| 追加合法空成员（6） | 容器摘要变；解码内容相同，账本仍须记录两个成员 | 内容相同，但未消费末成员 |
| 改坏 CRC、ISIZE、截最后 1 B（各 6） | 固定完整门、Python/Node 整包及首成员均拒 | 没有可用的完整首成员 |
| 合法首成员＋坏 CRC 次成员（6） | 固定完整门、Python/Node 整包均拒 | 6/6 仍解出原文并通过有限终态，但未验次成员 |
| 加单零尾或单非零尾（各 6） | 本地完整覆盖合同均拒；实测两库整包只兼容零尾 | 仍可解首成员；不是尾字节已消费的证据 |

另有两个小合成正反例：首成员解码产出 60 B 并通过有限终态，次成员解码再产出 10 B、又派发一帧；完整 gzip 可解，但拼接后的有限终态拒绝；UTF-8 的一个汉字跨成员边界，必须先拼接字节再按文本解析。成员拼接后的内容相等也不代表容器原字节相等。

## 复核边界

62 个固定案例为 6 原件、18 等价派生、36 近错及 2 小合成；不是 62 次产品运行。旧原件保持不变；UTF-8 例是实际选定的合成补对照，不把所有精确试件都说成提前锁定。项目内非作者独立枚举成员边界与校验字段，再与结果对照；Python/Node 本次都依赖 zlib，不算异实现认证或老师要求的受控第三方核验。

契约限已归档小数据；标准库零填充兼容不是本地证据合同的漏受，也不据此判供应商不合规。只分清压缩容器覆盖、解码内容和有限终态三个结论，不推现实传输缺失、改写旧 R2 分数或冻结规范。
