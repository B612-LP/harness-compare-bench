# 分层表示的联合等价核查（试行）

**问题。** 单改一层不翻转裁定，不保证把多层变化放在一起仍然等值。沿用 [SSE 终态与内容分账](<../SSE终态与内容完备分账-2026-11-27/README.md>)、[精确数字](<../精确数字与字符串域隔离-2026-11-27/README.md>)及 [gzip 成员覆盖](<../gzip成员覆盖与解码等值-2026-11-27/README.md>)三个有界观测面，在同一批既有响应试这件事，不新增产品试次或修改既有失败。

## 固定四轴

29个已有客户端捕获是父支持：21 Chat、8 Responses；原本的6个gzip响应都是Chat。每父生成16个组合：LF／CRLF；单 `data`／在JSON对象左花括号后分成两个 `data` 行；原数字词面／只把实际整数型小数 `0.0` 和 `1.0` 改为同值小数 `0E+0` 和 `10e-1`；单／双gzip成员。`[DONE]` 保持标记，不当JSON。四轴限定和数据范围是看过现有档案后确定的；所有组合都重新套gzip，包括参考格及原先未压缩的Responses，不是新的捕获。恢复解码时，先消费全部成员、拼接原解码字节，再解UTF-8和物理帧。

| 分层断言 | 有界观察 |
|---|---|
| 压缩后字节相同 | 0／464，各自的gzip派生都不同于归档容器。 |
| 解码后的整条SSE逐字节相同 | 100／464。 |
| 按空行派发并合并 `data` 后，每帧载荷逐字节相同 | 200／464。 |
| 事件标签、固定终态门、规范内容序列一致 | 464／464。原有1540个JSON载荷在16格重用，24,640次比较不是独立观察。 |

96个原小数词分布在24个父载荷，0.0及1.0各48；每种词在改词格分别重写384次，不改变整数或字符串。64个实际双成员切点切在UTF-8码点中间，两片各自不能解UTF-8；拼齐后闭合且值相等。先各解每片与先合字节不是同一个操作。

## 负例不是同一种失败

两种响应族各取一父、在固定位置做六种改动，合成对照与464组合分账：

| 改动（每族各一） | 首个可见差异 |
|---|---|
| 在JSON键字符串内部拆 `data`；去掉末空行派发所需的最后一LF；改成错误 `event` | 三类各2，物理派发或SSE对象门拒；分段插入并非总是合法等价。 |
| 新增合法数词 `1e6145` | 2例仍有SSE闭合，但超出试行精确指数帽；不是JSON语法错。 |
| gzip尾附非成员 | 2例在全成员消费即拒，没有进入内容比较。 |
| 新增合法未知JSON字段 | 2例都闭合且能规范化，但规范内容确实不同，不是入口故障。 |

**结论和边界。** 这四种固定改写共同出现时，没有使这29父的有限裁定翻转；逐层的“相同”不能互换，12控制也不是穷举。内部非作者分开用逐字节帧状态机、数词扫描和分类型指纹重做组合，并在既有测量器上对照，核心计数及明细相符；共享底层JSON／zlib，不是独立实现认证或受控第三方。原响应和完整逐项复算留在受控原档，公开页只给聚合。不能据此认证HTTP传输、一般供应商协议、服务端实际摄入、读取真值、因果或排名；试行口径不冻结，正式25格与旧分不变。
