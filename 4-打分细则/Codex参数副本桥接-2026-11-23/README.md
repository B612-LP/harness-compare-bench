# Codex 流中的参数副本：流内一致不等于原件绑定

[试行 0.2](<../CodexResponses观测口径-2026-11-23/README.md>)分别核对「分片拼接＝参数完成事件」和「条目完成事件＝最终信封」，但这两项不能证明前后两组携带同一参数。复核了试行页原来的 **12 份冻结捕获，内有 7 个函数调用**，没有新运行。这次只问：能否把最终条目当作该流最初给出的参数？

## 四份参数如何对齐

按物理次序，以同一条目 ID 与输出数组位置对齐：由片段拼接的 **A** → 参数完成事件 **B** → 条目完成事件 **C** → 最终信封内条目 **D**。核对事件先后，再比较解出的参数原串 UTF-8 字节，不把内嵌 JSON 重编码。原件另核同包请求、响应的摘要和长度；语义等价或结构成立不能代替这个身份门。

| 对照 | 旧流结构门接收 | 核对四份参数后接收 | 与预先固定的原件绑定 |
|---|---:|---:|---:|
| 原件 | 12/12 流 | 7/7 调用 | 12/12 包 |
| 只换 LF→CRLF | 12/12 流 | 参数不变 | 0/12 包 |
| 只同步改 C、D（等长） | 7/7 | 0/7 | 0/7 |
| 只同步改 A、B（等长） | 7/7 | 0/7 | 0/7 |
| 同步改 A、B、C、D（等长） | 7/7 | 7/7 | 0/7 |
| 只错绑 B 的输出位置 | 0/7 | 0/7 | 0/7 |

等长改值只改变内嵌 JSON 的 `cmd` 值，不执行命令。局部改写使 B 与 C 不同；若只看流的两端各自是否自洽，14 个局部派生变体都会漏判。相反，四份副本同步改变后仍自洽，新桥也会接收；**这不是绕过原件绑定**，固定摘要从未接收任何变体。原件 7/7 一致，所以这不是原档曾出现参数不一致的证据。各变体复用原件，不是额外试验，更不是漏判率。
