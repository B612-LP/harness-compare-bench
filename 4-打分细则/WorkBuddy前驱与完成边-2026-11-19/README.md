# WorkBuddy 归档对照：前驱边与工具完成边

**前驱边不是完成边。** 两份已存档派生件中，四个定向选取的片段共有 7 条调用、7 条结果。片段内 10/10 条可比的 `parentId` 边指向紧邻的上一条记录；但把结果直接挂到前驱，只有 1/7 条与作用域内的 `callId` 配对一致，3/7 条挂到另一调用，3/7 条的前驱是另一结果。前驱边在这里仍是有效的记录关系，应单独保留。

| 片段 | 工具类别 | 记录角色顺序 | 结果 → 直接前驱 | 结果 → 作用域内调用 | 分歧 |
|---|---|---|---|---|---|
| A1 | Read | 调用、调用、结果、结果 | 3→2；4→3 | 3→1；4→2 | 1 条挂到不同声明目标；1 条前驱为结果 |
| A2 | Read | 调用、结果 | 2→1 | 2→1 | 正对照，两种配对重合 |
| A3 | Bash | 调用、调用、结果、结果 | 3→2；4→3 | 3→1；4→2 | 1 条挂到另一调用；1 条前驱为结果；不判断命令或对象 |
| B1 | Read | 调用、调用、结果、结果 | 3→2；4→3 | 3→1；4→2 | 1 条挂到不同声明目标；1 条前驱为结果 |

序号仅在片段内有效。前驱法只查同一来源的直接记录边，不沿链回溯。完成配对同时要求来源、会话、请求、显式步骤和调用标识一致；调用与结果角色各恰好一条，调用记录更早，工具名一致。缺项、错作用域、重复或标签冲突均保留为无法绑定。7/7 条具备唯一的本地完成配对，且结果状态均记录为 `completed`。这是归档状态，不是结果准确、实际成功或任务验收的证明。

两条误挂的 Read 结果各自比较时，直接前驱所指调用与作用域内配对调用的**声明目标不同**；只比较结构化声明是否相等，不读取目标或核验正文。5 条 Read 结果中，前 512 个 UTF-8 字节内的完整首行未命中三种预设标题样式，计 **0/5** 条可采纳的目标断言。此处没有独立结果侧对象证据，不能认定真正成功或实际读取的是哪个对象。

两种只改一个字段的内存反例也区分了它们：只改前驱可翻转一处邻接而不改完成绑定或状态；只改匹配调用所属的请求范围，标识本身仍有唯一候选，但作用域内绑定变成未知，前驱和状态不变。反例不是新增运行。

## 本地复算与限制

在此目录执行 `python3 -B verify.py` 或 `python3 -B -O verify.py`。复算器校验序号、角色、较早调用、配对唯一性和固定片段类别，从受限表重新算出分母与分歧；不会打开源轨迹，不认证上游标识、原件真实性或外部对原件的访问与核验。能复算的是这个表的关系与计数，不是从任意归档提取配对。

这是 [Week 5 #17](https://github.com/B612-LP/harness-compare-bench/issues/17) 的局部观测示例，不修订旧分或宣布统一规范通过。片段不是随机样本，不估频率、覆盖率或偶然发生的概率；未测试 FIFO。结果不裁定调度、并行、因果、操作系统 I/O、原生运行、上游状态或产品效果。
