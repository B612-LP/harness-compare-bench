# SSE 分片：帧数相等、参数相等和捕获身份不是一回事

这次只复核既有客户端可见捕获：Codex Responses 12 个流，7 个闭合工具调用；DSH Chat 1 个自然缺参流。两边格式、样本与支持范围不同，不比较产品效果。原包仍以请求、响应双长度和双摘要绑定，表中离线派生都**不是原包**。

| 控制 | Responses（7 个实际调用） | Chat（1 个指定调用） |
| --- | --- | --- |
| 移动相邻片段分界、帧数不变 | 7/7 片段长度向量变，按键拼接的 UTF-8 与严格对象保持相同 | 不入围 |
| 将一片拆为两帧 | 7/7 帧数和片数各加一，连续序号按原流逐位核对；完整参数不变 | 不入围 |
| 参数一处等长改值 | 7/7 拼接长度和片段长度向量不变，精确文本与严格对象均变 | 1/1 等长改变已返回的值；缺必填字段的事实没有因此改变 |
| 把一片分给错误位置 | 7/7 无索引拼接不变，按工具键的参数确认拒绝 | 不入围 |
| 去末 dispatch | 7/7 不再确认闭合参数 | 1/1 不再确认，不能据此报缺参 |

Chat 原样的 27 个参数片段都带其他工具字段，不满足预先限定的「纯片段」，因此两项重分片和错位控制都不是零失败，而是**零入围**。原样闭合对象上的两个必填顶层字段，一个缺失，另一个存在且顶层类型符合当次声明；不等于完整 JSON Schema 校验。

两种额外近错进一步暴露了边界：Responses 新片复制旧序号，旧结构门与四副本参数一致检查仍接受 7/7；受影响的是物理序号，不抹去已经一致的参数副本。将整流序号改在另一连续基数下也不能通过与原捕获序号的逐位比较。Chat 新的非目标参数键使用非法名称或同包未声明名称时，不确认整个参数投影；同包唯一声明的合法名称可作对照。不能只用平拼接、参数尺寸或序号连续性验收。

聚合结论经项目内部非作者从受限原件重投影并对照。它不证明服务端原帧边界、其他流格式或 Harness 效果，不替代受控第三方原件核验，不改变旧门与成绩。联读[参数副本桥接](<../Codex参数副本桥接-2026-11-23/README.md>)与[自然缺参链](<../响应侧工具参数源头-2026-11-17/README.md>)。
