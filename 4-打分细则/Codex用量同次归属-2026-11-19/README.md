# 同次 Codex 会话：响应计数、原生用量与镜像分账

## 观察

在一份既有 Codex CLI 会话中，三个客户端 `response.completed` 的响应 ID 各自精确对应一条同轮原生主用量记录；并非拿相等的计数配对。五个共同字段共 **15/15** 逐条相等，分别累加的每步前缀也 **15/15** 相等。另三条原生日志的累计镜像无独立响应 ID：按同轮身份、位置及结构关联，每条镜像对应一条主记录；它们不是另三次工具或模型调用。

## 证据与比较

本次针对[已有客户端响应计数](<../Codex响应侧计数与缓存抖动-2026-11-17/README.md>)中一条三个响应的固定主链，补做同次原生对照；与[既有其他 15 槽的原生账本](<../首条产品计数等值复核-2026-11-16/EXECUTION-RECORD.md>)分开，不合并样本。三条响应分别有 234、115、46 帧。共同线程/轮次、完成的输出项、前两次的后继请求工具历史和收尾区间一并核对；主用量由响应 ID 定位，累计镜像只在相应原生区间凭结构附着，不给它补 ID。

| 受检响应序位 | input | cached input | output | reasoning output | total |
|---|---:|---:|---:|---:|---:|
| 1 | 8,117 | 4,608 | 348 | 133 | 8,465 |
| 2 | 8,533 | 8,320 | 229 | 4 | 8,762 |
| 3 | 8,821 | 8,576 | 34 | 25 | 8,855 |
| 各面分别求和 | 25,471 | 21,504 | 611 | 162 | 26,082 |

表中是两面均分别取得并相符的自报计数；缓存输入是输入的子项，推理输出是输出的子项，不在 total 上再加两次。客户端完成响应未提供缓存写入字段，而相应原生视图显示 0；派生里的 `wire_cache_write: null` 仅标记原字段缺失，不是客户端回了 `null`。这项跨面等值未知，不能填 0 后把它算作第六个共同量。

## 何处可辨认，何处仍歧义

把前两条响应的数值交换、保留原身份和位置，配对不改，但第一步累计不再相等；到第二步两项会抵消。故终值同和不足以补证逐条等值。只把一个等值镜像的线程改成另一线程，受影响镜像归属不可核，不改三条有直接 ID 的主记录。上述是离线软件对照，不是新场次。对最终消息阶段标签的合成错法未被原型泛用门全部识别；本次实际阶段匹配另由内部非作者确认，不将该工具称为通用认证器。

## 外推与复核

这只说明同一历史会话在固定覆盖内的记录一致，不认证生成方向、供应商来源、计费、真实缓存或实际推理工作。在这次研究中未新增产品、模型或网络试验，未改旧报告和正式 25 格；项目内部从固定原件单独投影，不等于受控第三方核验。

[公开派生](<evidence.json>)只保留数值和绑定类别，不含原件、身份、正文或轨迹定位。`python3 -B verify.py --self-test` 复算该派生的逐项等值、累加和数值互换反例；对错线程及阶段缺口仅核对登记状态，不能独立认证响应 ID、镜像作用域或原始来源。[第五周验收要求](<../../反馈/2026-11-18-第五轮/验收条款-公开版.md>)。
