# 规范字节的整包预算：等长不等同一原件

在[固定精确数字候选](<../精确数字与字符串域隔离-2026-11-27/README.md>)下分别问：整份 JSON 对象的输出字节会不会增长？原、规范两种长度相同，又能说明什么？本文只比 UTF-8 对象载荷，不含流帧、压缩、JSONL 行尾、内存、token 或费用。

## 单数词限额不限制整对象宽度

对两个固定实现共同接受的对象，原载荷长 \(n\)、规范长 \(m\)，有 **`2m ≤ 3n`**，且 3/2 不能降低为更小的统一比例。证明要点：结构、布尔和 null 不长；按 Unicode 标量重编码字符串与键不长，键排序不改总长，语法空白只减少。数词以原长 `L`、增长 `Δ` 计：整数与零不增长；非零十进制输出的调整后指数受限于 ±6144，至多增长 5 字节，故 `L≥9` 时 `2Δ≤L+1`。在 `L≤8`，无指数的非零小数只可能长至多 2；有指数的，省下的点号与零抵消可能增宽的指数。因此每个增长数词连同一个不同的紧前结构字节（`:`、`[` 或 `,`）可支付两倍自身增长，总和不超过输入长。

取 `{"a":[1.1,…]}`，放 `j` 个 `1.1`，原长为 `4j+7`，每项改为 `11e-1` 后为 `6j+7`。数词仍只 3 字节、对象深度固定，却多 `2j` 字节；8,192 项的合成实算是 **32,775 → 49,159 B**。两个实现另核 10,112 项短词形状与边界合成，包括这组宽例；不是穷举所有对象。[旧词元闭包反例](<../精确数词的输出闭包-2026-11-27/README.md>)讨论单个数词，和本页整对象预算不能互代。若另定输入 `n≤B`，可保守预留 `floor(3B/2)` 输出字节；这不限制解析内存，也不声明实现可读取任意大的对象。

## 1,804 个既有位置：长度都一样，字节几乎都不同

| 固定支持 | 原与规范等长 | 仅键顺序不同 | 键顺序和数字词面不同 | 原规范字节相同 |
|---|---:|---:|---:|---:|
| 旧 R2 独立重投影请求 | 29 | 29 | 0 | 0 |
| 同批 SSE JSON 数据载荷 | 1,540 | 1,516 | 24 | 0 |
| 三份公开 JSONL 的记录 | 235 | 234 | 0 | 1 |

在每个位置上，语法空白、键和值字符串、数词、结构以及布尔/null 的分量长度净差都为零。这不是跨对象抵消，也不等于每个词元没改写，24 个响应就有同长数词改写。这里只把每个原对象与其自己的规范输出比，不推出两次运行的行为同异；[R2](<../wire请求面扩展-2026-11-27/README.md>)与[原档及派生分母](<../同日观测支持集与派生分母-2026-11-27/README.md>)给出原分母，本文不再把它们计作新样本。

等长也可能来自抵消，而非上表机制：`{"a":1.1  }` 中数词增 2 字节，空白减 2，原规范等长却不同字节；把 5 个多余输入字节放在键的 Unicode 转义或外部语法空白，可产生相同输入长度、相同规范字节与相同净差，原因却不同。JSON 字符串里嵌了文本，不因此把内层按 JSON 再解释。
